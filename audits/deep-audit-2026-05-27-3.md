## ROOT CAUSE (one-line)

`Island.addMember(entity, groupId)` only appends to `super.members` when `groupId == MOD_UUID` (the "Members" group). Every other path - custom groups, the GUI's direct `group.addMember()` bypass, even the save-time copy constructor - leaves players in a group but **off** the canonical members list. The save path then serialises `super.members` (the truncated list) and overwrites the on-disk NBT. On reload, `Island.isPartOf(uuid)` returns false, `getIslandByEntityUUID` returns null, and the player sees "You can not execute this command without having an island." The island isn't actually gone - the player's membership got silently deleted on the last save.

## CRITICAL

- [x] [core/src/main/java/yorickbm/skyblockaddon/core/islands/Island.java:167] `addMember` only adds to `super.members` when `id.equals(MOD_UUID)`. Custom-group and Visitors-group adds skip the members list entirely, so they vanish on serialise.
  why: serializeNBT at ForgeIsland.java:259-263 only writes `super.members`. Any member who lives only in a custom group's set never reaches NBT. After restart they are not in the members list anymore and `isPartOf` (Island.java:230-232) returns false.

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/islands/ForgeIsland.java:44-58] Save-time copy constructor amplifies the bug: iterates `island.getMembers()`, looks up each member's group, and re-adds them via the same broken `addMember(m, customGroupId)`. Members assigned to custom groups get dropped from the copy's `members` list, and that copy is what gets written to disk.
  why: `SkyblockAddonWorldCapability.saveNBTData` (line 62-64) calls `getIslands().stream().map(ForgeIsland::new)`. Even though the live in-memory island has `members` correct (or correct-ish - see next finding), every save round-trip produces a corrupted on-disk copy. Stop the server, start it back up, members are gone.

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/enhanced/ScrollableListGui.java:319-336] The `set_group` GUI handler bypasses `Island.addMember` entirely - calls `oldGroup.removeMember(p)` + `targetGroup.addMember(p)` directly. The member's slot in `super.members` is never touched, so they're already inconsistent before the save bug even fires.
  why: Players using the in-game group GUI to reassign a member to a custom group hit this path. After reassignment, member is in the custom group's set, but `Members` group's set may still contain them too (oldGroup is whichever `getGroupForEntityUUID` returned first - HashMap order). The next save copy then truncates them. This is the most common user-visible trigger.

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/events/Gui/IslandGuiEvents.java:241] `event.getIsland().addMember(playerUUID, groupUUID)` goes through `Island.addMember`, which (when groupUUID is custom) removes the player from all groups first and then fails to add them back to `super.members`. Same data-loss outcome as the GUI bypass above, via a different door.
  why: This is the "members_group" GUI flow. Same corrupted state, same save-time loss.

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/commands/IslandAddGroupMemberCommand.java:91] `/island group <name> addMember <player>` calls `group.addMember(target)` directly, bypassing Island.addMember. Same bug class - target is now in a custom group but not in `super.members`.
  why: Server has command access to this path. Players using the command-line group management hit this too.

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/commands/IslandCreateCommand.java:58-72] Island creation runs on a `new Thread(...)` - off the server thread - and from that worker calls `cap.genIsland(level)` (places blocks in the world), `IslandManager.registerIsland(...)` (mutates the `HashMap` singleton), and `newIsland.teleportTo(executor)` (teleports a server player). The off-thread move itself is intentional (gen is slow on a busy server and would lag the main thread); the bug is that block writes and singleton mutations stayed on that worker.
  why: Minecraft world state and `HashMap` are not thread-safe. `getIslandByEntityUUID`, `saveNBTData`, and `onWorldSave` all iterate `islandsByUUID.values()` on the server thread. If a player runs /island create while a save fires (or while two players create at once), the iteration can throw `ConcurrentModificationException` or skip/duplicate entries during a rehash. CME from inside `getIslandByEntityUUID`'s slow-path stream propagates up uncaught and the lookup returns null - exactly the "lost island" symptom. This is the most likely explanation for *sporadic* loss when the data on disk looks fine.

## HIGH

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/events/ModEvents.java:65-72] Two save paths race: `WorldEvent.Save` writes `getIslandsFromCache()` with no copy, and `SkyblockAddonWorldCapability.saveNBTData` writes `getIslands().map(ForgeIsland::new)` with the broken copy. Both target the same `islanddata/*.nbt` files. Whichever runs last wins.
  why: If the broken copy runs last, every island on disk gets the truncated members list. If the cache-filtered save runs last, only the in-cache subset survives - inactive owners' islands keep whatever the broken copy wrote.

- [x] [core/src/main/java/yorickbm/skyblockaddon/core/islands/IslandManager.java:20,30-34,147] `islandsByUUID` (HashMap), `reusableLocations` (LinkedList), `lastLocation` (Vec3i) are all mutated from the IslandCreateCommand worker thread with no synchronization. Save iteration (line 62 in SkyblockAddonWorldCapability and line 71 in ModEvents) reads these from the server thread.
  why: Backs CRITICAL above. Plain HashMap mutated during iteration is undefined behavior - rehash during another thread's stream can lose entries or loop forever.

- [x] [core/src/main/java/yorickbm/skyblockaddon/core/islands/IslandManager.java:189-201,54] `getIslandsFromCache()` only returns islands whose owner/member UUIDs are currently in `CACHE_islandByPlayerUUID`. Cache cap is `maxPlayers * 2.5`. Server has 104 islands (per logs); a 40-player server has a cap of 100. Any island whose owner hasn't logged in within 12h (or got LRU-evicted) gets skipped by `onWorldSave`.
  why: Admin commands or programmatic changes to an inactive owner's island don't get persisted via this path. Capability `saveNBTData` does cover all islands but it's the broken-copy path. Either way, inactive islands are saved either incorrectly or not at all.

- [x] [1.18.2/src/main/java/yorickbm/skyblockaddon/util/NBTEncoder.java:126-152] `saveToFile` writes directly to the target path with no temp-file-and-rename. Crash mid-write truncates the file; `loadFromFolder` (line 108-117) catches the load failure and silently logs `Failed to load '<file>'` - the island is dropped from memory on next start.
  why: Compounds the other bugs. If the JVM dies during a save (OOM, kill -9, hardware), the island whose file was being written becomes load-time-corrupt and disappears from the in-memory map entirely on next boot. Worst-case "lost the whole island" outcome.

- [x] [core/src/main/java/yorickbm/skyblockaddon/core/islands/IslandManager.java:42-46] `initializeData` `put`s islands into `islandsByUUID` without `clear()`ing first. If `loadNBTData` ever runs twice in the same JVM (capability re-attached after `/reload` or some plugin lifecycle), stale islands from the previous load remain alongside the new set.
  why: Not the primary bug, but a latent corruption source. Stale entries would also pollute the caches.

- [x] [core/src/main/java/yorickbm/skyblockaddon/core/islands/IslandManager.java:58-71,86-88] Both `CacheLoader`s call `islandsByUUID.values().stream().filter(...)` and propagate exceptions through `ExecutionException`. `loadIslandIntoReverseCache` (line 86-88) wraps that in `throw new RuntimeException(e)` - a CME during player login becomes a crash/error spam, and the join-time cache prime fails.
  why: When the worker-thread mutation races a player login, the join's cache prime throws. Subsequent /island commands then have to take the slow path, which can hit the same race again.

## Recommended next actions

1. **Fix `Island.addMember`** (core/src/main/java/yorickbm/skyblockaddon/core/islands/Island.java:155-170): add the entity to `super.members` regardless of which group they're being assigned to (or pick the single rule "everyone on the island is in `members`, groups are an orthogonal tag"). This single change neutralises CRITICALs 1, 2, 3, 4 and 5 because the broken save copy will now retain every member.
2. **Route the GUI/command bypasses through `Island.addMember`** (ScrollableListGui.java:329, IslandAddGroupMemberCommand.java:91) so the `members` list stays canonical. Direct `group.addMember` calls should be banned outside of `Island`.
3. **Keep `/island create` off-thread for the slow parse, but bounce the unsafe parts onto the server thread.** Reverting to a fully main-thread create is not an option - gen is slow on a busy server and would stall the tick. Instead: the worker thread can still parse the structure NBT (the palette/blocks for-loops at SkyblockAddonWorldCapability.java:112-128). The block placement (line 137), chunk/heightmap reads (line 139-140), `IslandManager.registerIsland(...)`, and `newIsland.teleportTo(executor)` must run on the server thread - wrap them in `server.execute(() -> ...)` or schedule onto the next tick. The chunked-over-time pattern already used by AdminPurgeCommand's `ChunkTaskScheduler`/`IslandChunkManager` (AdminPurgeCommand.java:137,149) is probably the right template - spread block placement across ticks instead of dumping the whole island into one tick. Off-thread world writes are the most likely cause of the *sporadic* loss when the on-disk data looks intact.
4. **Atomic NBT writes**: write to `<uuid>.nbt.tmp`, fsync, then `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)` in NBTEncoder.saveToFile so a mid-write crash can't truncate a file.
5. **Either pick one save path or make them coherent**: have `onWorldSave` and `saveNBTData` go through the same writer using the same source-of-truth collection. Right now the two paths disagree on which islands to write and how to copy them.
