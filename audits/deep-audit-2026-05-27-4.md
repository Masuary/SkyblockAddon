The core member-loss fix is correct and deployable. The four parallel review agents flagged many "criticals" but cross-checking against actual code paths showed most were speculative or matched pre-existing behavior. Real findings below are minor; safe to ship to the production Linux+ext4 server.

## HIGH

- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/util/NBTEncoder.java:144] Fallback catches `IOException` (broad), not specifically `AtomicMoveNotSupportedException`. Masks real I/O errors on non-ext4 deployments.
  why: Intended to handle "filesystem doesn't support atomic move," but on NTFS/NFS a permission-denied or disk-full would silently degrade to plain replace. Irrelevant for Linux ext4 production.

- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/commands/IslandCreateCommand.java:60-69] Cooldown check-then-set is TOCTOU: `hasActiveCooldown` reads then `cooldowns.put` writes - two atomic ops, not one compound. Two concurrent creates from same player within microseconds both pass.
  why: `Collections.synchronizedMap` synchronizes individual ops only. Server-thread race re-check at IslandCreateCommand.java:88-92 catches the actual race so worst-case is second create short-circuits with "already has island." Negligible real impact.

## MEDIUM

- [ ] [core/src/main/java/yorickbm/skyblockaddon/core/islands/IslandManager.java:43-48] `initializeData` clears the maps but does NOT invalidate the Guava caches. Only matters if `loadNBTData` runs again in the same JVM (`/reload`). Caches retain stale entries for 12h after reload.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/commands/IslandCreateCommand.java:114] Daemon worker thread + ungraceful JVM shutdown mid-gen can leak one cooldown + one grid slot. Non-daemon would block JVM shutdown, which is worse.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/capabilities/SkyblockAddonWorldCapability.java:217] `getHeight(Heightmap.Types.WORLD_SURFACE_WG, ...)` reads a heightmap that `LevelChunk.setBlockState` does NOT update. Pre-existing behavior (original code went through same setBlockState path). Switching to `WORLD_SURFACE` would be technically more correct.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/islands/ForgeIsland.java:44-65] Copy constructor cannot recover pre-existing on-disk member corruption: iterates `island.getMembers()` which is already truncated. Custom-grouped members lost on previous saves stay lost. Forward-fix only; would need a separate one-shot repair pass to undo historical corruption.

## LOW

- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/util/BuildingBlock.java:17-19] `place(...)` method is unused after the refactor. Dead code worth removing or marking legacy.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/capabilities/SkyblockAddonWorldCapability.java:128] `bigestX`/`bigestZ` misspelled (should be `biggest`). Carried over from original.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/commands/IslandAddGroupMemberCommand.java:92] Failure-path uses `commands.group.not.found` language key but the failure case is "target is owner" - misleading.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/capabilities/SkyblockAddonWorldCapability.java:209-213] `ClientboundLevelChunkWithLightPacket(..., null, null, false)` may briefly send stale light to clients tracking the chunks. Matches the AdminPurge pattern (IslandChunkManager.java:108) so it's consistent; resolves on next light tick.
- [ ] [1.18.2/src/main/java/yorickbm/skyblockaddon/commands/IslandCreateCommand.java:107-109] If `registerIsland`/`teleportTo` throw inside the success branch, the cooldown stays set (exception escapes the inner try). Vanishingly unlikely; neither normally throws.
